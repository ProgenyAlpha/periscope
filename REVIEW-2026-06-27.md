## Dimension summaries

### concurrency (4 findings)

Two genuine data races exist in the new diff-introduced code, both flaggable by `go test -race`. Neither the existing hub design nor the watcher loop have race conditions — the hub is a textbook single-goroutine event loop with correct mutex use, and the watcher uses a single-goroutine event loop with non-blocking timer callbacks. The concurrency design is generally sound. The two races are both on package-level `time.Time` variables that are read and written from goroutines that run concurrently in normal server operation. A third structural issue exists in `broadcastJSON` where a blocking channel send is called from the watcher's flush path without a non-blocking escape, making the watcher's event consumption susceptible to stalling. Hub goroutine shutdown is missing a ctx.Done() arm but is cosmetically harmless since the process exits immediately after `startServer` returns.

### security (6 findings)

The server is fundamentally localhost-only (default bind 127.0.0.1, CheckOrigin restricted, CORS restricted), which blunts most attack surface. No OAuth token is ever logged, echoed to the dashboard, or stored outside the in-memory client struct — that flow is clean. The installer writes files with controlled content from embedded defaults, no command injection. The six real issues found are: a CheckOrigin prefix match that enables Cross-Site WebSocket Hijacking (CSWSH) from a page on any domain starting with "localhost"; a non-constant-time bearer token compare; token leakage into URL query strings and access logs; PII-containing profile cache written world-readable; the SQLite DB (which stores the VAPID private key and push subscriber crypto keys) created with umask-default permissions; and a minor CORS misconfiguration that sends permissive headers to rejected origins.

### forecast-correctness (6 findings)

The codebase has one critical division-by-zero that produces +Inf in a JSON-serialized struct (breaking the dashboard response when all weekly rate-limit growth occurs during CLI-inactive windows), one fully wired burn-rate file with no callers (the dollar burn feature is unreachable), and a defensive gap in the weekly window elapsed-hours formula that produces a wildly inflated rate if the API ever returns a reset time beyond 168 hours. Pricing fallback, token-weight accounting, and cache-hit rate are internally consistent. The 5-hour linear projection in the statusline segment and the blended history-based projection in the hook telemetry use materially different formulas for the same quantity, producing values that silently diverge for the same session. No integer truncation errors exist in the cost computation path because TransformUsage already rounds utilization before JSON round-trip. burn.go's anomalous use of `any` as a variable name shadows the built-in but is harmless at runtime.

### data-sqlite (8 findings)

The data layer is structurally sound for a single-writer, single-process tool, but has several concrete correctness defects. The most impactful are: (1) zero SQLite busy_timeout with two goroutines writing concurrently means every watcher-flush that races against the polling loop silently drops imported rows; (2) the migration helper runs each DDL + schema_version update as two separate un-transacted Exec calls, which is safe only because the current two migrations are IF-NOT-EXISTS idempotent — the next non-idempotent migration will corrupt on crash; (3) BuildDashboardData defers rows.Close() inside if-blocks for all three queries, keeping connections open when CalcPhantomUsage opens three more, and none of these eight call sites ever check rows.Err(), so iteration errors produce silently truncated results; (4) ImportJSONL's "skip if count >= len(lines)" dedup strategy conflates row count with line count, producing permanent duplicate inserts whenever any malformed line was previously skipped. The remaining findings are lower-stakes races on two unprotected time.Time globals and a timezone inconsistency in limit_history.ts that breaks lexicographic SQL ordering in non-UTC locales.

### uncommitted-diff (8 findings)

The diff is a coherent multi-part feature: 5-level effort ramp (xhigh/max), live-effort propagation via ~/.periscope/effort/ files, a /v1/messages header-based polling path to avoid the oauth/usage 5-req budget, adaptive poll interval, and manual-sync cooldown. The HTML widget changes (runtime.html, rate-limits.html, session-list.html) are well aligned with the DashboardData.LiveEffort JSON field added in store/db.go. The forecast.go format change is cosmetic and consistent. However, the diff is not in a committable state: burn.go is untracked with zero callers anywhere, StatuslineInput.RateLimits is parsed but never consumed (promised feature left half-built), and two package-level time.Time globals are written from concurrent goroutines without synchronization. Additionally, the effort segment in the statusline omits the "max" case, and a debug dump is unconditionally written on every keypress.

### go-idioms-resources (8 findings)

The codebase is well-structured and mostly correct. The hook paths (hookStop, hookDisplay) do not produce stray stdout writes — all slog calls route to stderr via the default handler, and the two intentional fmt.Print calls are the prescribed JSON output. The polling goroutine has a recover(). However there are eight concrete defects: one nil-pointer panic reachable directly from the display hook (hookRecordSnapshot discards f.Stat() error then immediately dereferences the result), one timer leak in the polling select, three places that use the default HTTP client with no timeout (could block a handler goroutine or the CLI indefinitely), the webpush library defaulting to a no-timeout http.Client that can stall both the polling goroutine and the health watchdog, a data race on the package-level lastManualSync time.Time, a silently-discarded write error in hookDisplay's history path, and a pattern of discarding http.NewRequest errors leaving nil-req dereferences one URL typo away.

The dashboard's XSS defenses are inconsistent. `escHtml()` is defined and correctly applied everywhere session labels, summaries, project paths, and model names reach `innerHTML` — but two innerHTML sinks in `_slDetailRow()` (session-list.html) skip it for tool names, creating a real XSS path via MCP server tool names written to sidecars by Claude Code hooks. ### drift-hooks-statusline (2 findings)

Two concrete drift points found. First and most impactful: the installer prints "StopTurn" as the hook event name to configure in Claude Code settings, but the actual event Claude Code fires is "Stop". Because registerHooks() never writes ~/.claude/settings.json — it only prints manual-setup instructions — every user who follows the printed output configures the wrong event name and hookStop() is never invoked. This silently kills turn-by-turn cost accounting and transcript processing; the dashboard shows stale or empty session data. Second: the StatuslineInput struct tags the vim mode field as json:"vim_mode" but Claude Code's statusline stdin payload delivers it under the key "vim" (dot-path vim.mode per official docs). The field is always nil; the vim segment never renders. The UserPromptSubmit additionalContext JSON shape (hookSpecificOutput wrapper, hookEventName, additionalContext) matches the current spec exactly — no drift there. The rate_limits, effort, cost, context_window, model, and workspace struct tags are all correct.

### drift-telemetry-source (6 findings)

Periscope was built when Claude Code had no native rate-limit awareness, so the architecture revolves around polling Anthropic's OAuth API and an unofficial `/v1/messages` header-ping path. Since Claude Code v2.1.80 (now v2.1.132+), this premise has changed: Claude Code emits `rate_limits.five_hour` and `rate_limits.seven_day` natively in the statusline stdin JSON for Pro/Max users, making the polling loop partially redundant. Periscope's code already defines a struct to receive that native data (`StatuslineInput.RateLimits` in statusline.go) but then silently discards it — the statusline and display hook both read the polling-based cache file instead, which means the freshest rate-limit data Claude Code hands periscope is thrown away on every statusline render. Separately, periscope uses the Claude Code OAuth token to call `/v1/messages` directly (the primary polling path added in the diff), which Anthropic's February 2026 policy statement explicitly prohibits. The unofficial sub-windows (`seven_day_oauth_apps`, `seven_day_cowork`) have no corresponding headers and are not preserved in the cache-supplement logic, causing silent data loss between hourly OAuth refreshes. These are a mix of a real correctness gap (native data discarded), a policy-compliance risk (OAuth token on `/v1/messages`), and a documentation mismatch (the README's stated premise is no longer accurate).

### drift-feature-gaps (7 findings)

Periscope's most urgent gaps are pricing table correctness for the current model generation: Fable-5/Mythos-5 and Sonnet-4-6 are both absent from every pricing surface (Go map, JS constant, shipped TOML), so sessions using those models show silently wrong costs — 2x undercount for Fable-5 and ~1.7x overcount for Sonnet-4-6 due to the Opus fallback. Beyond pricing, four genuine feature gaps exist: Fast Mode doubles token billing but is invisible to periscope; Claude Code now emits live rate-limit percentages in its statusline payload but periscope ignores them in favor of the file cache only; all models in claude.toml are stamped 200K max_input when 1M-context is now standard; and Claude Code's native OTEL export path could provide latency and span data the hook transcript parser can never reach. None of the gaps require architecture changes — they are additive table entries, struct fields, or an optional new ingestion goroutine.

- **Location:** `internal/analytics/phantom.go:143-153`
- **Dimension:** forecast-correctness · **Category:** concurrency · **Severity:** critical → high

**What / why:** The guard at line 144 checks `totalPct < 0.5 || phantomPct < 0.5` but does NOT guard against `cliPct == 0`. **Suggested fix:** Change the guard to: `if totalPct < 0.5 || phantomPct < 0.5 || cliPct <= 0 { return &PhantomData{LocalSessionTotal: ..., Source: "rate_delta", Confidence: "estimated"} }`. **Verifier reasoning:** The division-by-zero is real and reachable. At phantom.go:115 `cliPct` starts at 0.0 and is only incremented inside the `if hasActivity` branch (line 137). When every pctWeekly-increasing interval is CLI-inactive, `cliPct` stays exactly 0.0 and `totalPct == phantomPct`; if that phantom growth is >= 0.5pp, both guard conditions are false and execution reaches line 153 `phantomCost := localTotal * (phantomPct / cliPct)`. `localTotal` is guaranteed > 0.001 by the line 48 check, so this is positive/0.0 = +Inf (Go float div never panics). ### [MEDIUM] Data race: lastManualSync read and written by concurrent HTTP handler goroutines

- **Location:** `server.go:641, 650, 662`
- **Dimension:** concurrency · **Category:** concurrency · **Severity:** high → medium

**What / why:** `lastManualSync` is a package-level `time.Time` with no synchronization. `handleUsage` is registered as an HTTP handler; net/http dispatches each request in its own goroutine. Two concurrent POST /api/usage requests will simultaneously read (line 650: `time.Since(lastManualSync)`) and write (line 662: `lastManualSync = time.Now()`) the same struct. `time.Time` is a 24-byte, 3-field struct (`wall uint64`, `ext int64`, `loc *Location`); it is not atomically accessible on any architecture Go supports. The race detector fires on this pattern. Practical consequence beyond torn reads: the check-then-set is not atomic, so two goroutines can both observe the cooldown as inactive and both proceed to fire `fetchAndCacheUsage`, burning two of Anthropic's ~5-per-90min OAuth budget tokens in one burst — exactly the budget leak the cooldown is designed to prevent.

**Evidence:** var lastManualSync time.Time
// line 650 (read, goroutine A and B simultaneously):
if since := time.Since(lastManualSync); since < 5*time.Minute {
// line 662 (write, both goroutines):
lastManualSync = time.Now()

**Suggested fix:** var (
    lastManualSync   time.Time
    lastManualSyncMu sync.Mutex
)

// in handleUsage:
lastManualSyncMu.Lock()
sinceSync := time.Since(lastManualSync)
if sinceSync < 5*time.Minute {
    lastManualSyncMu.Unlock()
    // serve cached...
    return
}
lastManualSync = time.Now()
lastManualSyncMu.Unlock()

**Verifier reasoning:** The data race is real. server.go:641 declares `var lastManualSync time.Time` with no mutex/atomic. handleUsage reads it at line 650 (`time.Since(lastManualSync)`) and writes it at line 662 (`lastManualSync = time.Now()`). The server (server.go:432-451) is a stock `http.Server` with `ListenAndServe()`, and the middleware chain (authMiddleware→rateLimitMiddleware→corsMiddleware→mux) does not serialize handlers — net/http runs each request in its own goroutine. The only lock in this path is inside rateLimiter.allow() (server.go:1239), which protects only the limiter's own tokens; externalLimiter has burst=3 (server.go:1254), so up to 3 concurrent `POST /api/usage` requests pass and enter handleUsage simultaneously. So two goroutines genuinely read/write the same unsynchronized 3-field time.Time concurrently — a true data race per the Go memory model; `go test -race` fires on it. The check-then-set TOCTOU (read at 650, write at 662) is also real: both goroutines can observe the cooldown inactive and both call fetchAndCacheUsage.

**Verifier notes:** Severity dropped high→medium for two reasons. (1) Blast radius: this is a localhost-bound (app.Config.Server.Host), auth-token-gated, CORS-localhost-only single-user dashboard; concurrent POST /api/usage needs multiple tabs, a double-click, or poll-overlapping-manual-refresh — occasional, not sustained. (2) The finding's budget-leak claim is overstated: fetchAndCacheUsage (server.go:1031) now uses a cheap /v1/messages header ping as its PRIMARY path (~$0.00001, comment at lines 1048-1050); the tight ~5-per-90min /api/oauth/usage endpoint only runs on the periodic needsOAuthRefresh window or on header-ping failure. ### [LOW] Non-constant-time bearer token comparison

- **Location:** `server.go:1202-1208`
- **Dimension:** security · **Category:** security · **Severity:** medium → low

**What / why:** authMiddleware compares the supplied bearer token using Go's `==` operator on strings. String comparison in Go short-circuits on the first differing byte, making the comparison time vary with the length of the common prefix. A local attacker (or any code running on the same machine) with access to sub-millisecond timing can mount a byte-by-byte timing oracle and recover the token character-by-character. The query-parameter path at line 1207 has the same issue. For localhost-only deployment the window is narrow but not zero: a malicious process on the same host can make thousands of requests per second.

**Evidence:** server.go:1202-1208:
if r.Header.Get("Authorization") == "Bearer "+token {
    next.ServeHTTP(w, r)
    return
}
if r.URL.Query().Get("token") == token {
    next.ServeHTTP(w, r)
    return
}

**Suggested fix:** Use crypto/subtle.ConstantTimeCompare for both checks:
  import "crypto/subtle"
  supplied := r.Header.Get("Authorization")
  expected := "Bearer " + token
  if subtle.ConstantTimeCompare([]byte(supplied), []byte(expected)) == 1 { ... }
  // same for the query param path

**Verifier reasoning:** The code does exactly what the finding describes. server.go:1202 compares `r.Header.Get("Authorization") == "Bearer "+token` and server.go:1207 compares `r.URL.Query().Get("token") == token`, both using Go's `==` string operator, which compiles to runtime.memequal and short-circuits on the first differing byte (and on a length mismatch). No HMAC, no hashing, no constant-time path anywhere — grep confirms no crypto/subtle import or ConstantTimeCompare. So the technical premise ("non-constant-time comparison of a secret") is genuinely present.

However, "medium" overstates practical risk, so I downgrade to low:

1. Threat model is weak. main.go:144 defaults Host to 127.0.0.1 (localhost). The token is supplied by the operator via a config TOML on disk (main.go:48) or the PERISCOPE_TOKEN env var (main.go:242-243). Any process on the same host running as the same user — the exact attacker the finding posits — can read the token directly from the config file or /proc/<pid>/environ. A nanosecond-scale timing oracle is strictly dominated by these trivial local exfiltration vectors; an attacker who can already run code locally has no reason to mount it.

2. Practical exploitability is near-zero. The leaked signal is a single short-circuited byte comparison over a ~32-char token — sub-nanosecond to low-nanosecond. It is buried under Go HTTP-stack jitter: goroutine scheduling, GC, syscall overhead, mux routing, and the prior path checks at 1195-1200. Direct-equality token timing oracles are widely regarded as impractical even over loopback; extracting a per-byte signal would require an astronomically large, clean sample set the noise floor does not permit.

3. Auth is optional anyway (1190: empty token disables it entirely), and this is a personal Claude Code usage dashboard, not a multi-tenant secret store.

The issue is a real best-practice deviation with a correct one-line fix, but the impact is hardening-tier, not medium.

**Verifier notes:** Fix is correct and idiomatic: subtle.ConstantTimeCompare([]byte(supplied), []byte("Bearer "+token)) == 1 for both the header and query-param paths. Caveat: ConstantTimeCompare returns 0 immediately on a length mismatch, so it still leaks token length (the attacker controls the supplied length) — acceptable and standard, but not fully length-oblivious. nit is also a defensible severity; low is the most I'd justify given the localhost default and that the token already lives in a readable config file / env var, which any same-host attacker can read without any timing side channel. Relevant file: /home/progenyalpha/Desktop/Apps/periscope/server.go:1189-1213.

### [LOW] ImportJSONL positional dedup breaks permanently when any prior line was malformed

**Verifier reasoning:** The underlying defect is real but the finding materially overstates it. ### [data-sqlite] BuildDashboardData defers rows.Close() inside if-blocks, leaving 3 connections open when CalcPhantomUsage opens 3 more

The finding's central mechanism is wrong. ### [go-idioms-resources] time.After(backoff) in polling select leaks the timer on context cancellation

The cited code at server.go:362-369 matches the description — a `for { select { case <-ctx.Done(): return; case <-time.After(backoff): } }` polling loop with backoff reaching maxInterval=60m. But the finding's core mechanism is false for this codebase. go.mod declares `go 1.25.7` and the installed toolchain is go1.25.7. Since Go 1.23, the runtime garbage-collects unstopped, unexpired timers (including the channel from time.After) the moment they become unreferenced, instead of holding them in the timer heap until they fire. When the goroutine returns on ctx.Done() (line 364-366), the pending time.After timer at line 368 is unreferenced and reclaimed promptly. The "runtime timer heap holds the timer until it fires 60 minutes later" behavior the finding describes was specifically eliminated in Go 1.23. Independently, the magnitude is trivial: the loop blocks on the select so at most ONE timer is ever outstanding (not accumulating per-iteration), and the only route to ctx.Done() is graceful shutdown (line 365 logs "polling shutdown") where the process is exiting and all timers die with it. So even on pre-1.23 Go this would be a single small allocation in a terminating process — nit, not medium.
